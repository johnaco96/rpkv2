# Node Lifecycle Commands

Ticket 14.2 adds `nodectl`, a small operator CLI for repeatable validator node
lifecycle workflows.

These commands do not claim production readiness. They make initialization,
configuration validation, status checks, storage repair, snapshot file handling,
and version reporting repeatable.

## Init

```powershell
cargo run --bin nodectl -- init --validator-id validator-a --node-dir nodes/validator-a
```

This creates:

- `nodes/validator-a/keys/` with validator identity files generated by
  `identityctl` helpers;
- `nodes/validator-a/storage/`;
- `nodes/validator-a/run/`;
- `nodes/validator-a/snapshots/`;
- `nodes/validator-a/production.toml.template`.

Copy `production.toml.template` to `production.toml`, then replace every peer
placeholder before starting. A fresh node cannot safely start production traffic
until peer identity values are filled in and config validation passes.

## Validate Config

```powershell
cargo run --bin nodectl -- validate-config --config nodes/validator-a/production.toml
```

Bad config fails before network start. Validation uses the same
`ProductionConfig::load` path as the server.

## Start

```powershell
cargo run --bin nodectl -- start --config nodes/validator-a/production.toml
```

By default this is a dry run. It validates config and prints the server command
that would be used:

```powershell
server --mode production --config nodes/validator-a/production.toml
```

To execute the server command from `nodectl`, pass `--exec`:

```powershell
cargo run --bin nodectl -- start --config nodes/validator-a/production.toml --exec
```

Operators should prefer the dry run in automation until service supervision,
PID management, logging, and restart policy are configured externally.

## Status

```powershell
cargo run --bin nodectl -- status --config nodes/validator-a/production.toml --pid-file nodes/validator-a/run/node.pid
cargo run --bin nodectl -- status --config nodes/validator-a/production.toml --json
```

Status reports:

- whether config validates;
- validator id when config is valid;
- storage directory and scan cleanliness when available;
- PID file value when provided.

The PID check is intentionally conservative: it reports a PID file presence but
does not prove the process is healthy. Use health/readiness endpoints for live
process health.

## Stop

```powershell
cargo run --bin nodectl -- stop --pid-file nodes/validator-a/run/node.pid --remove-pid-file
```

This command reads the PID file and optionally removes it. It does not kill a
process by default; process termination should be handled by the service
supervisor until a safe cross-platform shutdown RPC exists.

## Repair Ledger

```powershell
cargo run --bin nodectl -- repair-ledger --storage-dir nodes/validator-a/storage --policy fail-startup
cargo run --bin nodectl -- repair-ledger --storage-dir nodes/validator-a/storage --policy quarantine-corrupt
```

This uses the existing storage recovery scanner. `fail-startup` reports
corruption without moving files. `quarantine-corrupt` moves corrupt slot files
into the storage quarantine directory and rescans.

## Snapshot And Restore-Snapshot

```powershell
cargo run --bin nodectl -- snapshot --input snapshots/source.rpsn --output nodes/validator-a/snapshots/local.rpsn
cargo run --bin nodectl -- restore-snapshot --input nodes/validator-a/snapshots/local.rpsn --output nodes/validator-a/snapshots/restore.rpsn
```

Both commands decode and validate the snapshot before copying it. This provides
safe local file handling for existing snapshot artifacts. It does not yet create
a live snapshot from a running node.

## Version

```powershell
cargo run --bin nodectl -- version
```

The version output includes crate version, git commit, build features, and build
profile.
