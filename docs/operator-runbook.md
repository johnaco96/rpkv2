# Operator Runbook

This runbook describes how to build, configure, start, observe, rotate, revoke,
benchmark, and roll back the current research prototype. It documents the code
as it exists now and is not a production-readiness claim.

## 1. Clean Checkout

```bash
git clone git@github.com:johnaco96/rpkv2.git
cd rpkv2
git status --short --branch
```

Expected branch for a normal checkout:

```text
## main...origin/main
```

## 2. Build

Use the default feature set for production-like builds. The default enables real
Ed25519 verification.

```bash
cargo build --release
cargo test --features ed25519
cargo clippy --all-targets -- -D warnings
```

Do not use `--no-default-features` or `--features insecure_demo` for production
or production-like validation. Production binaries intentionally fail to build
without real Ed25519 support.

## 3. Feature Flags

- `ed25519`: real Ed25519 packet verification. This is enabled by default.
- `insecure_demo`: explicit demo-only stub crypto path. Do not enable for
  production.
- `dalek_batch`: optional Ed25519-related batch feature.

Production mode rejects insecure feature combinations.

## 4. Key Provisioning

Generate validator TLS private keys and SPKI pin files out of band. Do not
commit generated keys, SPKI pin files, wallet files, `.env` files, cloud
credentials, or seed material.

The local TLS private key must be PKCS#8 PEM. Peer TLS pins must be PEM
`PUBLIC KEY` files containing SubjectPublicKeyInfo bytes.

Recommended directory layout outside Git tracking:

```text
keys/
  validator-a.key
pins/
  validator-b.pub
store/
```

If using the demo binary, it may generate local `server.key` and `server.pub`
files. Production mode refuses ephemeral generated keys and requires a config.

## 5. Config File

Create a TOML config from this template and replace every placeholder:

```toml
format_version = 1

[local]
bind_address = "0.0.0.0:4433"
validator_id = "validator-a"
private_key_path = "keys/validator-a.key"
packet_signing_key_path = "keys/packet-signing.key"

[[peers]]
validator_id = "validator-b"
ed25519_verify_key_hex = "64_hex_characters_for_peer_packet_verify_key"
address = "203.0.113.20:4433"

[[peers.tls_spki_pins]]
path = "pins/validator-b.pub"

[replay]
slot_window = 1024

[queues]
raw = 8192
deduped = 8192
verified = 8192
packed = 8192
bank = 1024
poh = 1024
shred = 4096
signed = 4096

[rate_limits]
packets_per_second = 50000
bytes_per_second = 64000000

[storage]
directory = "store"
allow_unsafe_demo_storage = true
recovery_policy = "fail_startup"
flush_interval_records = 1
flush_interval_ms = 1
sync_data = true

[processing]
verifier_workers = 1
verifier_batch = 256
signer_batch = 256
signer_workers = 1
# verifier_affinity_base = 2

[metrics]
bind_address = "127.0.0.1:9100"

[gossip]
peer_ttl_seconds = 60

[[gossip.bootstrap_peers]]
validator_id = "validator-b"
gossip_address = "203.0.113.20:4434"
transaction_ingress_address = "203.0.113.20:4433"
repair_address = "203.0.113.20:4435"
```

Important current limitation: `allow_unsafe_demo_storage = true` is required
because the current append-file storage backend is pilot/demo storage, not
validator-grade blockstore storage.

Configured validator mode uses mutual raw-public-key TLS. The server presents
`local.private_key_path` as its transport RPK and rejects inbound peers whose
presented SPKI is not active in the peer registry. The configured client also
presents `local.private_key_path` while pinning the selected peer's SPKI.

Validate before startup:

```bash
cargo run --bin server -- --mode production --config config/production.toml --check-config
```

Validation happens before binding sockets.

## 6. Peer Registry Setup

For every peer, configure:

- `validator_id`: the operator-assigned peer identity.
- `ed25519_verify_key_hex`: the peer packet-signing verification key as 64 hex
  characters.
- `packet_signing_key_path`: the local validator packet-signing private key
  generated by `identityctl` or `nodectl init`; required for the configured
  server pipeline.
- `address`: optional network address used by identity-aware clients.
- `tls_spki_pins`: one or more active TLS SPKI pin files.
- `revoked_spki_pin_paths`: optional emergency denylist entries.

Peer SPKI pins authenticate transport identity. Packet-signing keys authenticate
validator packets. Keep these keys separate and review the validator id, SPKI
pin, and packet verification key together during onboarding and rotation.

Duplicate validator ids fail startup. Duplicate SPKI pins across validators fail
startup. Revoked SPKIs fail startup even when also configured as active.

Optional gossip bootstrap peers are discovery seeds, not identity authorities.
The validator id must be known in the validator set, and dynamic peer updates
must arrive as signed rpkv2 gossip announcements before they are trusted.

## 7. Ports and Firewall

Validator node inbound:

```text
UDP 4433 from allowed validator peers
TCP 9100 only from localhost or monitoring network
TCP 22 only from operator admin IPs
```

Benchmark receiver inbound:

```text
UDP 9000 from benchmark sender IP
TCP 22 only from operator admin IPs
```

Keep metrics bound to `127.0.0.1:9100` unless a protected monitoring network is
in place.

## 8. Startup

Production-like server:

```bash
cargo run --release --bin server -- --mode production --config config/production.toml
```

Configured client smoke test:

```bash
cargo run --release --bin client -- \
  --mode production \
  --config config/production.toml \
  --peer-validator-id validator-b
```

Demo-only local server:

```bash
cargo run --bin server -- --mode demo --bind 127.0.0.1:4433
```

Production mode without config must fail:

```bash
cargo run --bin server -- --mode production --check-config
```

Expected error:

```text
Error: production mode requires --config
```

## 9. Metrics

Metrics are exposed on the configured metrics address. For the default config:

```bash
curl http://127.0.0.1:9100/metrics
curl http://127.0.0.1:9100/health
curl http://127.0.0.1:9100/readiness
```

Watch these during startup and traffic:

- packet received and accepted counters;
- malformed, replay, stale-slot, bad-signature, and unknown-peer drops;
- queue depth and queue-full drops;
- verification latency and batch size;
- storage write and storage error counters;
- active connections and per-peer traffic.

## 10. Logs

Start with info logs:

```bash
RUST_LOG=info cargo run --release --bin server -- --mode production --config config/production.toml
```

Logs include mode, validator id, peer id where known, connection id, slot,
packet type, and rejection reason where applicable. Logs must not contain
private keys, PEM contents, wallet material, or cloud credentials.

## 11. Shutdown

Use Ctrl-C or the service manager stop command. The server marks health as
shutting down, requests coordinated shutdown, closes the QUIC endpoint, waits for
connection tasks, and joins the metrics endpoint.

Manual local stop:

```bash
Ctrl-C
```

After shutdown, verify no process is still listening on the validator port or
metrics port.

## 12. TLS SPKI Rotation

Use Unix seconds in UTC. Keep clocks synchronized with NTP and make overlap
windows longer than expected clock skew plus deployment time.

1. Generate the new TLS private key and SPKI pin out of band.
2. Distribute the new peer SPKI pin file to validators.
3. Add both old and new pins:

```toml
[[peers.tls_spki_pins]]
path = "pins/validator-b-old.pub"
valid_until_unix_seconds = 1893456000

[[peers.tls_spki_pins]]
path = "pins/validator-b-new.pub"
valid_from_unix_seconds = 1893452400
```

4. Validate config:

```bash
cargo run --bin server -- --mode production --config config/production.toml --check-config
```

5. Restart peers during the overlap window.
6. After the cutoff, remove the old pin or leave it expired.

## 13. Emergency Peer Revocation

If a TLS SPKI is compromised, add it to the revoked list:

```toml
[[peers]]
validator_id = "validator-b"
ed25519_verify_key_hex = "64_hex_characters_for_peer_packet_verify_key"
revoked_spki_pin_paths = ["pins/validator-b-compromised.pub"]

[[peers.tls_spki_pins]]
path = "pins/validator-b-current.pub"
```

Validate and restart immediately:

```bash
cargo run --bin server -- --mode production --config config/production.toml --check-config
cargo run --release --bin server -- --mode production --config config/production.toml
```

Packet-signing key revocation is not yet equivalent to TLS SPKI revocation. Treat
packet-signing key compromise as a blocking incident and rotate config across all
peers.

## 14. Rollback

Rollback is a code and config operation:

```bash
git fetch origin
git checkout <known-good-commit>
cargo build --release
cargo run --bin server -- --mode production --config config/production.toml --check-config
cargo run --release --bin server -- --mode production --config config/production.toml
```

Before rollback, preserve logs, metrics snapshots, and storage files for review.
Do not roll back to a commit that re-enables insecure crypto or removes required
production guardrails.

## 15. Benchmark Procedure

Use disposable benchmark nodes. Do not copy production secrets to benchmark
nodes.

Receiver:

```bash
git clone git@github.com:johnaco96/rpkv2.git
cd rpkv2
bash scripts/setup_receiver.sh
bash scripts/run_receiver.sh
```

Sender:

```bash
git clone git@github.com:johnaco96/rpkv2.git
cd rpkv2
bash scripts/setup_sender.sh
RECEIVER_IP=<receiver_public_ip> bash scripts/run_sender.sh
```

Raw command equivalents:

```bash
cargo run --release --bin fast_rx -- \
  --mode benchmark \
  --bind 0.0.0.0:9000 \
  --workers 1 \
  --verify on \
  --dedupe on \
  --out-csv receiver.csv
```

```bash
cargo run --release --bin fast_tx -- \
  --mode benchmark \
  --target <receiver_public_ip>:9000 \
  --pps 50000 \
  --payload 256 \
  --duration-secs 60 \
  --signing on \
  --out-csv sender.csv
```

Build a combined summary:

```bash
cargo run --bin bench_summary -- \
  --tx benchmarks/results/two-node/sender.csv \
  --rx benchmarks/results/two-node/receiver.csv \
  --sender-meta benchmarks/results/two-node/sender.meta.json \
  --receiver-meta benchmarks/results/two-node/receiver.meta.json \
  --payload 256 \
  --out benchmarks/results/two-node/summary.json
```

Do not commit generated CSV, JSON, log, archive, key, or credential files.

## 16. Dry Run Checklist

From a clean checkout:

```bash
cargo fmt --check
cargo build
cargo test
cargo build --features ed25519
cargo test --features ed25519
cargo clippy --all-targets -- -D warnings
cargo run --bin server -- --mode production --check-config
cargo run --bin fast_rx -- --mode benchmark --help
cargo run --bin fast_tx -- --mode benchmark --help
```

The production-without-config command should fail with `production mode requires
--config`. The benchmark help commands should succeed.
